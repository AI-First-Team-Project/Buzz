# Buzz AI 서버 구조 원칙

## 목적과 현재 범위

Buzz는 FastAPI를 단일 백엔드로 사용한다. 별도의 Node 백엔드나 메시지 브로커를 추가하지 않고,
모델 추론·자동 분석·사업장 상태·이력·가상 문 제어를 FastAPI 애플리케이션 안에서 책임별로
분리한다.

현재 모델 → FastAPI → Android/Web 사용자 테스트 흐름과 자동 분석 상태 전환은 구현되어 있다.
이 문서는 다음 단계인 지속 분석 실행기와 모니터링 기능을 일관된 구조로 확장하기 위한 기준이다.
MySQL 구현은 별도 담당자가 진행하므로 이 단계에서는 인터페이스와 책임만 정의한다.

## 임시 판정 정책

| 정책 | 임시 기준 |
|---|---:|
| 말벌 판정 | `P(wasp) >= 0.7` |
| 위험 상태 전환 | 말벌 판정 3회 연속 |
| 위험 자동 해제 | `non_wasp` 판정 3회 연속 |
| 위험 수동 해제 | 허용 |

이 값은 `app/config.py`에서 환경변수로 덮어쓸 수 있다. 단일 분석 응답과 사업장 상태를 구분한다.
한 구간이 `wasp`로 판정돼도 즉시 사업장을 위험으로 바꾸지 않고, 상태 서비스가 연속 판정 횟수를
확인한 뒤 상태를 전환한다.

## 구분 원칙

- Router는 HTTP 입력 검증과 응답 변환만 담당한다.
- Service는 분석, 상태 전환, 자동 폐쇄 같은 업무 규칙을 담당한다.
- Repository는 저장소 접근만 담당하며 업무 규칙을 포함하지 않는다.
- Worker는 사업장별 음원 공급과 실행 주기를 담당한다.
- Predictor는 모델 로드와 확률 추론만 담당한다.
- Web/Android는 서버 상태를 표시하고 사용자 명령을 전송한다. 모델 판정이나 위험 정책을 복제하지 않는다.
- 하위 계층이 Router나 화면 코드에 의존하지 않도록 의존 방향을 한쪽으로 유지한다.

```text
Router → Service → Repository
             ├──→ Predictor
Worker → Service
Web/App → Router
```

## 목표 폴더 구조

```text
ai_server/app/
├─ routers/
│  ├─ analysis.py          # 테스트·자동 분석 HTTP API
│  ├─ monitoring.py        # 사업장 상태·이력 조회 API
│  ├─ gate.py              # 수동 문 제어 API
│  └─ simulation.py        # 시연용 Worker 제어 API
├─ services/
│  ├─ analysis_service.py  # 전처리·추론·응답 조합
│  ├─ inference_service.py # Predictor 호출과 동시 실행 제한
│  ├─ state_service.py     # 연속 감지·해제 및 상태 전환
│  └─ gate_service.py      # 자동·수동 문 정책
├─ repositories/
│  ├─ site_repository.py
│  ├─ detection_repository.py
│  └─ gate_repository.py
├─ workers/
│  └─ audio_simulator.py   # 사업장별 독립 음원 공급 작업
├─ services/predictor.py   # 실제 모델 로드·추론
├─ schemas.py              # 외부 데이터 계약
├─ config.py               # 환경별 설정
└─ main.py                 # FastAPI 구성과 생명주기
```

실제 리팩터링은 기능을 연결하는 시점에 필요한 모듈부터 순차적으로 진행한다. 빈 계층이나 사용하지
않는 추상화만 미리 만들지 않는다.

## 지속 분석 처리 흐름

사업장 3개는 OS 스레드 3개로 고정하지 않고 서로 독립적인 세 개의 논리적 작업으로 취급한다.
각 작업의 실패와 재시도 상태는 분리하되 모델은 한 번만 로드한다.

```text
사업장별 음원 공급 작업 3개
        ↓
사업장별 대기열에서 현재 구간을 하나씩 수집
        ↓
최대 3개 입력 배치 전처리 → 모델 1회 추론 → 사업장별 원시 판정
        ↓
상태 서비스가 연속 판정 횟수 계산
        ↓
사업장 상태·이력·문 상태 저장
        ↓
Web/Android 조회 또는 실시간 수신
```

모델은 한 번만 로드하고 최대 3개 사업장 입력을 하나의 배치로 추론한다. 배치 결과는 입력 순서의
사업장 ID에 맞춰 분리한다. 한 사업장의 구간이 준비되지 않았을 때는 짧은 제한 시간 후 준비된
입력만 처리하므로 다른 사업장 작업을 중단시키지 않는다.

## 상태 관리 원칙

- 원시 분석 결과, 사업장 현재 상태, 문 상태를 서로 다른 개념으로 관리한다.
- 연속 `wasp` 횟수와 연속 `non_wasp` 횟수는 사업장별로 관리한다.
- `DANGER` 전환과 해제처럼 의미 있는 상태 변화만 이벤트 이력으로 기록한다.
- 같은 상태가 반복될 때 알림과 문 제어 이벤트를 중복 생성하지 않는다.
- 수동 위험 해제와 수동 문 개방은 별도 명령으로 구분한다.
- 서버 재시작 후 상태 복구는 MySQL Repository가 연결될 때 구현한다.

## 모델 교체 원칙

모델 파일을 교체해도 Router와 Web/Android 데이터 계약은 변경하지 않는다. 새 모델은 다음 조건을
지켜야 한다.

- 서버 설정의 모델 이름과 실제 파일이 일치한다.
- 입력 전처리는 24kHz, mono, 2초 및 현재 Mel 설정과 호환된다.
- 출력은 `[non_wasp, wasp]` 순서의 두 확률이다.
- 확률은 유한한 0~1 값이며 합이 1에 가깝다.
- 모델 교체 후 서버를 재시작하고 계약 테스트를 실행한다.

## 다음 구현 순서

`state_service`의 상태 전환, 사업장별 음원 공급 Worker, 최대 3개 입력 배치 추론, 사업장 통합
상태 조회, Web/Android 상태·이력 2초 폴링 연결은 완료했다. 다음 순서로 진행한다.

1. 문 제어 화면을 서버 API에 연결하고 수동 위험 해제 정책을 분리한다.
2. 별도 담당자의 MySQL Repository를 Service 인터페이스에 연결한다.
3. 이력 영속화, 재시작 복구와 통합 시나리오를 검증한다.
